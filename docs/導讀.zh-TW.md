# 導讀：為什麼「證明」比「測試」更能保證不掉資料

寫給初學者（也就是這個專案的作者本人），讓你能在面試時把這個專案講清楚。

## 這個專案在做什麼？

它做了一個「寫入前日誌」（write-ahead log，簡稱 WAL）：一種讓磁碟更新「要嘛全部成功、要
嘛當作沒發生」的技術，就算中途斷電也一樣。更重要的是，它用 Lean 4 這個「證明工具」**數學
上證明了**這件事會成立，而不是只用測試去「碰碰看」。

## 一、為什麼測試不能保證「永遠不掉資料」？

測試就是「試很多種情況，看有沒有出錯」。但斷電可以發生在**任何一個瞬間**，組合多到天文數
字，你永遠試不完。測試能找到 bug，卻**不能證明沒有 bug**。

證明不一樣。證明是像數學課那樣，一步一步推導，結論對**所有情況**都成立——包含你沒想到的
那一種。這個專案的證明，Lean 的核心會逐條檢查，不接受任何跳步（`sorry`）。

## 二、寫入快取與同步屏障：用郵局來想

把磁碟想成郵局。

- 你把信丟進郵筒（`write`），**信還沒寄出去**，只是放在郵筒裡。你以為寄了，其實沒有。
- 郵差不定時來收信，而且**收信順序不一定照你投的順序**。
- 「同步屏障」（`sync` / flush）就是你站在郵局櫃台說：「把目前所有的信**現在**全部寄出，
  寄完再跟我說。」`sync` 回來，才代表前面寫的東西**真的進了硬碟**。
- 「斷電」就是郵局突然關門：郵筒裡還沒收的信，**每一封都可能寄到、也可能不見**，各自獨
  立。甚至可能寄出「半封信」（torn write，寫到一半的區塊）。

真實硬碟就是這樣（有快取、有重排、有屏障）。本專案的 `Crashproof/Disk.lean` 就是把這個郵
局模型寫成數學定義。

## 三、寫入前日誌怎麼保證「全有或全無」？

訣竅是：**先把要改的東西完整抄一份到「日誌區」，確認抄好了，再動真正的位置。**

1. 把這次交易要寫的新值，抄到日誌槽；`sync`（確定抄好了）。
2. 寫一個「標頭」說「這批有效，包含這些位置」；`sync`。**這一步是「成交點」。**
3. 照標頭把新值寫到它們真正該去的位置（install）；`sync`。
4. 把標頭清空；`sync`。

重開機時一定會跑「回復」：看標頭。如果標頭說「有一批有效」，就照它重做第 3 步（重做幾次
都沒差，結果一樣）；如果標頭是空的，就什麼都不做。

- 斷電在「成交點之前」→ 標頭還是空的 → 回復什麼都不做 → **回到交易前**。
- 斷電在「成交點之後」→ 標頭有效 → 回復重做安裝 → **跳到交易後**。

中間永遠不會出現「改了一半」的狀態。這就是「原子性」。

## 四、一條 Lean 定理長什麼樣子？

以「原子性」為例（`Crashproof/Theorems.lean` 裡的 `atomicity`），白話是：

> 如果在 commit 進行中任何一點斷電，接著做回復（回復本身再斷幾次都可以），那最後的邏輯磁
> 碟，**不是等於交易前的狀態，就是等於交易後的狀態**。

程式碼大致是：

```lean
theorem atomicity ... (hidle : Idle L m d) (he : Exec (commit L t) d (.crashed dc))
    (hx : CrashesTo dc x) (hr : RecoversTo L x df) :
    Idle L m df ∨ Idle L (applyWrites t m) df
```

`∨` 就是「或」，`m` 是交易前、`applyWrites t m` 是交易後。Lean 不接受你嘴巴說說，你必須真
的把推導每一步補完，它的核心才會認可。

## 五、什麼是「可信基礎」（trusted base）？

證明只保證「模型」與「協定」是對的。但底下還有一堆東西**沒被證明**，只能「選擇相信」：

- Lean 自己的核心、把程式編譯成執行檔的編譯器；
- 本專案唯一的那段 C 程式 `native/dev.c`（真正呼叫作業系統去讀寫、flush 硬碟）；
- 作業系統、硬碟韌體（如果硬碟謊報「我 flush 完了」，誰都救不了）。

誠實地把這些列出來，就是「可信基礎」。**所以我們還是要測試**——測試專門去打證明管不到的
那一塊。這個專案的當機測試（`harness/crashtest.py`）就是在做這件事：隨機在寫入途中斷電
2000 次，每次都檢查回復後的資料對不對，全過。

## 六、怎麼確定「證明真的有在把關」？突變測試

我們故意把協定改壞一行（例如：少一個 `sync`、先寫標頭再寫日誌、回復後不清標頭），然後看：

- 改壞「被證明的協定」→ Lean **編譯不過**（6 種都編不過）。
- 改壞「執行檔用的協定」→ 當機測試**抓得到錯**（7 種都抓到）。

這證明了證明和測試不是裝飾，是真的在擋 bug。

## 七、跟 wren-os 的比較（同一個作者的作業系統）

wren-os 也有一個一模一樣用途的日誌。我們把它的 `kernel/log.c` **原封不動**拿來，在同一套
模擬磁碟上跑同一套當機測試：也是 2000/2000 全過。

有一個有趣的差別：本專案在第 4 步清完標頭後會再 `sync` 一次；wren-os 不這麼做，改用
「checksum（CRC）」來分辨標頭是不是過期的。兩種都正確，但走的是不同的論證。wren-os 省了一
次屏障（比較快），代價是多了兩個假設（CRC 不會剛好撞到、標頭一個磁區會原子寫入）。這不是
bug，而是一個真實存在的設計取捨。`wren/reproduce.sh` 可以重現這個差別。

## 八、十個可能被問的面試問題（附簡答）

1. **為什麼不能只靠測試？** 斷電時機無限多，測試試不完，只能找到 bug、不能證明沒有 bug。
2. **什麼是寫入快取？** 硬碟先把資料放在易失的快取就回報「寫好了」，之後才真的寫到碟片。
3. **`sync`（屏障）保證什麼？** 它回來時，之前寫的所有東西都已經真的在碟片上了。
4. **WAL 為什麼能做到原子？** 先把完整副本寫進日誌並確認，標頭一寫就是成交點，之前斷電=
   沒發生，之後斷電=重做安裝。
5. **「回復具冪等性」是什麼意思？** 回復重複做幾次，結果都一樣，所以回復途中再斷電也安全。
6. **什麼是 torn write？** 一個區塊寫到一半斷電，前幾個磁區是新的、後面是舊的。標頭只佔一
   個磁區、磁區是原子寫入，所以壞掉的標頭會被 checksum 或解碼擋下。
7. **你的證明用了哪些公理？** 只有 Lean 的三個標準公理：`propext`、`Classical.choice`、
   `Quot.sound`，由 CI 用 `#print axioms` 自動把關。
8. **證明沒有涵蓋什麼？** 編譯器、那段 C、作業系統、硬碟韌體——也就是「可信基礎」。
9. **既然有證明，為什麼還要測試？** 測試專門打證明管不到的可信基礎那一塊，兩者互補。
10. **你跟 FSCQ 的關係？** 這是把 FSCQ 的想法（Crash Hoare Logic）用 Lean 重做一遍的學習
    專案，沒有宣稱原創、也與 MIT 無關。
